How to read these diagrams

Standard C4 notation. Each level zooms into exactly one element of the level above: the Context diagram's single system becomes the Container diagram; two of those containers are then decomposed into components. Every box carries its technology in monospace; every arrow is labelled with what actually crosses it.

The engine colour is not decorative. The system's central architectural rule is that LLMs reason and orchestrate; deterministic tools calculate — so which boxes are green and which are violet is the design.

Level 1

System Context

One system, one human role, two external dependencies. A media sales rep describes a campaign in prose and receives a validated inventory package they can quote to a client. The system reasons with a hosted LLM and reads a fixed analytical extract of the transit network.

What the system is responsible for — and what it refuses to do

ResponsibilityGuarantee it makes to the sales rep
Interpret the brief Never invents a budget, date, duration or geography the brief did not state — anything absent is returned in missing_information instead of imagined.
Quote a price Every price traces to quantiles of comparable historical contracted bookings. Where a human moved a price via a lever, the package says so explicitly.
Report an audience Reach is deduplicated across screens that see the same people. Gross exposures and distinct people are always reported as two different numbers.
Respect constraints Budget, availability, dates and geography are enforced in code. The LLM cannot reason a violation away, and a failed check is reported as a failure.
Handle the impossible Infeasibility returns reason codes and relaxation options. The system never assembles a plausible-looking package instead.

The three data layers, and why conflating them breaks things

LayerHolds Written byThe rule
DuckDB / CSV 166 MB of analytical truth: screens, bookings, ridership, POIs Nothing. Load-only. Never write to datasets/. Never scan the 2.05 M-row ridership file without usecols/dtype.
Artifact store Per-run intermediates: screen candidates, screen economics services/artifact_store.py Referenced by id. Rows never enter an LLM context — that is the entire point of the layer.
localDB Sessions, runs, uploads metadata, validation payloads, pricing levers services/local_db.py Application data only. No analytical rows, no uploaded file bytes, no large intermediates.
Upload stage The user's own brief documents api/uploads.py Untrusted. Validate type and size, never execute, never pass a whole document into agent context — extract and summarize first.

Run handles, not payloads. Every tool takes a run_id. The campaign spec, artifact references, pricing levers, optimization result and validation payload all live in run state; the model sees a handle plus a summary. This is what keeps a 250-screen candidate pool and a full price table out of a context window — and it is also why pricing levers live on the run rather than travelling inside a delegation message: a float that has to survive an LLM paraphrase is a float that will eventually arrive wrong.

Level 3a

Components — Agent Runtime

Zooming into the Agent Runtime container. One supervisor, two specialists, four tool surfaces totalling 16 tools, and a validation layer the Master must pass through before it is allowed to answer.

Validation Layer
agents/validation.py · deterministic · Master-owned
24 named checks across 9 families — cost, reconciliation, reach, inventory, geography, dates, hard constraints, availability, model confidence. Constraint checks fire only when the spec declares the constraint, and a check that cannot be evaluated is recorded as an explicit skip rather than a silent pass. Reach is recomputed independently here, not imported from the tool that reported it.
budget_respectedcost_reconciles reach_reconcilesreach_not_above_impressions curve_reach_boundedinventory_availability geography_eligibleno_duplicate_allocations min_zone_coverageexplanations_consistent …

Two specialists, not three. The reference architecture called for a third Data Intelligence agent over stage 2. It was removed: stage 2 is a fixed calculation, so an LLM shell around it bought only latency and a chance to paraphrase numbers wrongly. Delegation is reserved for stages where a specialist genuinely reasons about its own output.

Two tools deliberately absent from the UI stage rail. set_pricing_levers and get_client_negotiation_profile serve the conversation with the sales rep, not a pipeline stage. Mapping either one to a stage would advance the rail past stages that have not run, so they are unmapped — and neither creates a run, so neither is a pipeline entry point. A test pins that.

Level 3b

Components — Deterministic Engines

Zooming into the three engines. Nothing here calls an LLM, and nothing here does arithmetic on the model's behalf. Each engine is reached through exactly one thin tool wrapper, which maps run state in and Pydantic contracts out.

Audience Relevance Engine — stage 2, one file by design

Feature layer
app/data/db.py · DuckDB views
Demographics, POI draw and schedule-derived demand, resolved per screen × time block × day type.
v_screen_profilev_screen_demand_history v_schedule_blockv_route_block_demand v_corridor_block_demandv_screen_poi
Relevance scorer
transparent weighted sum
Five 0–1 components, no fitted model, fully explainable per screen.
audience 0.40geography 0.20 context 0.15time_of_day 0.15 booking history 0.10
Volume & pooling
pool_key deduplication
People passing per block, the reach ceiling after viewability, and the pool groups the optimizer dedupes on. transit_score is reported but deliberately not in the weighted sum — volume is the optimizer's objective, not a measure of fit.

Four units that must not be confused: a time block is 4 hours; a slot is one of 6 rotation positions cycling through it, so slot position is meaningless and slot count is share of voice. impressions_by_block is undiscounted people passing. reachable_daily_audience is the reach ceiling — distinct people, so it does not scale with slots or days. viewed_exposures_per_slot_per_day does scale with both.

Pricing Engine — stage 3, reached via ml_agent_tools

price_band
p25 / p50 / p90 of comparables
Segmented size × type × position × zone × daypart, each rung also split by deal shape, with a bounded 5-rung fallback ladder.
occupancy
day-by-day slot fill
6 slots per screen per block per day. The reported figure is the tightest single day across the flight, not an average.
price_optimizer
floor + occupancy × (cap − floor)
Seller-side price. Occupancy drives it. A price × P(booked) argmax was tried and rejected — it degenerates to the cap for every screen.
booking_probability
calibrated logistic
Reported as a diagnostic only, never as the price driver; within a segment the curve moves ~0.1–0.2%. Guarded by a coefficient sign check.
seasonality
day-of-week · holiday · event
Two terms weighted separately then multiplied, so a rep can keep an event premium while dropping the weekday haircut.
demand_value
merit vs realized price
The one signal that can disagree with history — and the only adjustment allowed to carry a quote above the band cap. Never sees a price. Four gates; +15% max.
client_profile
advisory · wired to no engine
The client's own realized price index and objection history, judged against its own standard error. Suggests a multiplier; only the rep may apply it.
levers
the agent-tunable surface
7 parameters, all identity by default, clamped in code rather than in the prompt. Weights dial influence, not magnitude: 1 + w(m−1).

The engine is a process singleton — get_pricing_engine(), ~9 s to build. Never constructed per request. What it does not compute is audience volume: pricing_internal_reach_proxy is quarantined, never mapped onto any exposure field, and is not reach.

Inventory Optimizer — stage 4, reached via or_agent_tools

config
provenance-tagged constants
Every constant tagged STRUCTURAL ASSUMED SOLVER so an assumed number can never be mistaken for a measured one.
exposure
the only unit conversion
People passing → viewed exposures. One implementation, one call site — because the constants are assumed, the single call site matters more than the values.
contract
input validation
Rejects a malformed or infeasible-on-its-face instance before a solve is attempted.
pooled
pool population
Builds the reachable population per pool_key × block, plus the reported saturation-curve diagnostic.
solver
MILP · HiGHS via SciPy · 1% gap
Maximizes reach directly: R ≤ min(E, P) is two exact linear constraints. Reports method, objective, gap and whether optimality was proven.
or_agent_tools._package_metrics
the reach definition
Not part of the formulation. This is the accounting the system stands behind, and the validator re-derives it independently.

optimization_method is self-describing, e.g. milp_highs_pooled_reach_min[reach,gap<=1%,optimal]. A feasible status means a valid plan inside the gap — not an error, and not a proven optimum.

Reach is never the sum of exposures. Screens sharing a pool_key — one stop, or one corridor — see the same people; on a 250-screen pool the naive sum over-counts by ~23×. The definition is Σ over (pool_key, block) of min(gross viewed exposures bought, that pool's reachable daily audience), both sides in viewed units.

One definition, three independent implementations, and that is on purpose: the OR tool computes it, the validator recomputes it, and the solver maximizes it. They must agree — and must never import one another, because agreement between independent implementations is the only thing being tested.

A validated number may not depend on an assumed constant. If a figure the validator checks moves with a constant nobody can measure, the check validates nothing about the one thing that is actually uncertain. This is why REACH_LAMBDA reaches only the reported diagnostic, and why curve_reach_bounded asserts a lambda-free bound instead of re-deriving the curve.

Dynamic view

The six-stage pipeline

Stages are strictly sequential — each consumes the previous stage's artifact. A supervisor can still try to delegate two at once, so every dependent tool checks its input via run_state.missing_prerequisite() and returns a recoverable prerequisite_missing result naming the producing stage. They never crash.

1
Brief intake & geography resolution Master
resolve_geography_terms → create_campaign_spec. Returns the run_id every later tool needs. Missing facts go into missing_information, never into an invented default.
CampaignSpec → run_state · creates the run
2
Audience & relevance scoring Relevance engine · 0 model calls
build_screen_candidates, called by the Master directly. Scores the eligible inventory, computes impressions and reach ceilings, assigns pool_keys.
artifact screen_candidates (parquet) → run_state
3
Pricing & availability delegated → ml_agent
estimate_screen_economics. Reads the run's pricing levers itself — they are never pasted into the delegation message — and returns pricing_levers_applied so the answer can say whether a human moved the quote.
artifact screen_economics (parquet) → run_state
4
Inventory optimization delegated → or_agent
optimize_package solves the MILP; compare_objectives puts the reach / awareness / frequency trade-off in front of the human. Infeasibility returns reason codes and relaxation options.
OptimizedPackage or InfeasibilityReport → run_state
5
Verification Master · the gate
verify_package — always, no exceptions. If it fails, the Master must name the failed checks and must not present the package as valid. A failed budget or availability check is never a matter of interpretation.
ValidationResult → run_state · status validated
6
Recommendation Master
inspect_package + check_explanations, then the Markdown answer the UI renders. Every screen-level claim must cite a real attribute — a zone, a price, an occupancy figure. "This screen is highly relevant" is not an explanation.

Not every turn runs the pipeline

Turn typeTriggerWhat happens
Opening brief get_active_run returns status: none Full pipeline, stages 1–6. ~90 s, ~17 model calls.
ANSWER (the default) A question about the existing package — why a screen, what a number means, what the risks are Read-only tools only. No spec, no candidates, no delegation. The answer is already in the run.
REBUILD A campaign input changed — budget, dates, geography, audience, goal, screen count, a hard constraint — or a lever moved Pipeline re-runs from stage 1. A new run_id is what tells the UI to show the stage rail again.

Two things this rule is not. A question that merely mentions a number is not a change — "why is the budget only 99.8% used?" is a question. And a hypothetical is not an instruction: the agent answers from the existing run and the price bands, then offers to rebuild rather than spending 90 seconds unasked.

Cross-cutting

Architectural decisions worth defending

Six choices that are visible in the diagrams above but not explained by them. Each was a deliberate departure from the obvious option, and each is pinned by a test.

Two specialists, not three
Departs from the reference architecture · agents/subagents.py

The spec called for exactly three specialists, including one over audience relevance. Stage 2 is a fixed calculation, so the LLM shell added latency and a chance to paraphrase numbers wrongly. Removing it also removed several model calls per run against a per-minute rate limit. Prefer a Master-owned tool over a subagent whenever a stage does not actually reason.

A MILP, not a greedy fill
app/optimize/solver.py

The four changes made to the ported formulation all point the same way. Reach is bounded by the exact min(E, P) rather than by tangent lines on an exponential curve with an assumed constant — the original left measured audience on the table and turned a 0.1 s solve into a 30 s timeout. The screen-count constraint counts screens, not (screen × block) cells. No 90% spend floor is invented, because no spec declares one. And the wear-out cap is a multiple of the flight's unavoidable exposure floor, because an absolute cap is satisfiable by no plan at all.

Clamp in code, not in the prompt
app/ml/levers.py

Out-of-range lever values are clamped and reported, never rejected. In an agent loop a rejected tool call becomes a retry against a per-minute rate limit — to reach the same number clamping would have returned directly. The tool result carries effective_levers and clamped, and the prompt requires the agent to quote what it got rather than what it asked for.

The one signal allowed to disagree with history
app/ml/demand_value.py

Everything else in the pricing engine answers "what did screens like this sell for?", which makes it a mirror — a screen always sold cheap is quoted cheap forever. The demand-value model scores what a screen physically delivers and never sees a price, because a model fitted to price treats the historical average as correct and would learn a systematically underpriced category as correct. It is the only adjustment permitted to exceed the band cap, and a test asserts nothing else can.

Advisory by structure, not by squeamishness
app/ml/client_profile.py

The client negotiation profile is wired to no engine, no lever default and no artifact. Price-driven loss rates are flat across leverage tiers (34.2 / 32.5 / 34.8%), so posture says nothing about whether a deal is lost — only what it settles at. Applying it automatically would mean pricing off the half of the finding that does not hold.

Honest failure over plausible output
api/campaign.py · agents/validation.py · run_state.py

Provider errors map to real HTTP statuses through provider-agnostic exception bases, so the mapping survives a provider swap. Infeasibility returns reason codes and relaxation options rather than a partial fill. And stub_stages plumbing is retained even though no stage is a stub and it now always returns [] — because it is the mechanism that would surface a regression.

Known limitations, surfaced by the system rather than hidden

LimitationHow the system handles it
Volume is schedule-derived only No ambient or pedestrian term, so block 1 (00:00–04:00) is zero for every screen despite 8,544 real block-1 bookings. The prompt requires the agent to state that a zero means "not modelled", never "nobody there".
Mobile screens have no demographics Zone is undefined for a vehicle, so all 2,615 of them score 0 on the demographic components — and the demand-value model gates them out entirely rather than scoring them badly.
No held-out accuracy metric for the audience model Which is precisely why no stage emits a per-screen confidence and the validator records model_confidence as an explicit skip.
A 30-day flight cannot deliver few exposures At 8 loop passes per trip, one slot on a saturated pool yields ~40 exposures per person over 30 days whatever the optimizer picks. The wear-out cap therefore constrains stacking, not total exposure — and the OR tool discloses the figure rather than implying it was tuned.
No conversion model exists A conversion goal weights the industry-to-POI context score as a proxy, and the agent is required to report the substitution explicitly rather than present the result as a conversion optimum.
