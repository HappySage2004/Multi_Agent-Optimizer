00Executive summary

Today a rep opens a spreadsheet, eyeballs the available screens, invents a price and sends a proposal. Nobody knows whether the price was right, whether those screens fit the audience, or whether three other advertisers wanted the same inventory that week. We replaced that with one conversation.

Sense
It reads the whole brief

The chat message and the attached RFP. Budget, flight dates, market list and mandatory zones are extracted from PDF/DOCX once at upload, so a one-line "see attached" still builds a complete spec — and a scanned PDF is reported as unreadable rather than silently ignored.

Plan
It reasons, then it calculates

The language models orchestrate, interpret and explain. Every number comes from a deterministic engine: a transparent relevance model, a pricing engine built on real contracted prices, and a mixed-integer program that proves its allocation optimal.

Adapt
It advises, and it listens

It asks up to three targeted questions when a brief is missing something load-bearing, ends every answer with costed suggestions, and turns what a rep knows — "this client never pays a peak premium" — into a re-priced package on the next turn.

The one principle behind all of it

LLMs reason; tools calculate — and every number is checked by something that did not produce it. The Master Agent never does arithmetic. It orchestrates four specialised systems, then runs 19 independent verification checks that re-derive reach, cost, availability, geography, dates and every brief-declared constraint from scratch. If a check fails, the package is not presented as sales-ready. That is the difference between a demo and something a rep can quote a client from.

How to read this document

It follows the C4 model. Context — who uses the system and what it touches. Containers — the deployable pieces and the three deliberately separate data layers. Components — four diagrams, one per subsystem, because the interesting engineering is inside them. Then a runtime view of a single turn, and two sections making the technical and the analytical case respectively.

01C1 · System Context

One platform, one human firmly in the loop, and four things outside our boundary: the advertiser, the rep's inbox, the model providers, and Urban Media's own data.

02C2 · Containers

A single-page Next.js workspace, one FastAPI process holding the agent runtime and three deterministic engines, and three storage layers that are deliberately never conflated.

03C3 · Components: the agent runtime

One Master Agent and two specialists — not five. Delegation is reserved for the stages where a specialist genuinely reasons about its own output; everything else is a Master-owned tool, because an LLM wrapper around a fixed calculation buys latency and a chance to paraphrase a number wrongly.

04C3 · Components: Audience & Relevance Engine

Deliverables D1 and D2 in one deterministic engine. It answers "who is near this screen, when, and why does that fit this campaign" for all 11,163 screens, and it uses every one of the five data layers to do it.

05C3 · Components: Pricing & Demand Forecasting

Deliverable D3. The specialist receives the shortlisted screens and the requested time blocks, and runs a nine-step decision for every screen × block combination — with each step's reasoning attached to the row it produced.

06C3 · Components: the OR Optimizer

Deliverable D4. Priced screens in, the best buyable package out — as a mixed-integer program that either proves its allocation optimal or explains, in reason codes and relaxation options, why no package exists.

07Runtime view: one turn, end to end

What actually happens in the ninety seconds between a rep pressing send and a quotable package appearing — and what happens on the turn after that, which is usually the turn that matters.

08Technical capabilities

Seven choices we would defend in a design review, not seven features on a slide. Each one exists because the obvious alternative was tried, measured, or would have failed on the sales floor.

1 · The agent guides. It does not just answer.

Most agent demos are a one-shot function call wearing a chat interface: brief in, wall of output out, and the human's judgement is nowhere in the loop. Ours is built the other way round — it is designed to be a colleague who knows the inventory and knows what it does not know.

Before the run
It asks, exactly once, and only about what matters

A brief with no audience named leaves 55% of the relevance weight sitting at a flat neutral value, and a brief with no advertiser category leaves another 25% — so the system would spend 90 seconds producing a confident ranking decided almost entirely by geography. Rather than hide that, it asks.

The gate is deliberately narrow: up to three questions, one round, at one moment only — after geography resolves and before the spec is built. Never mid-pipeline, never on a rebuild, never on a follow-up. Everything else has a defensible default and a recorded reason, and interrupting a 90-second run to buy one input is the fastest way to make a tool exhausting to use.

How it asks
Clickable options, not an open question

The agent supplies the two most probable answers for this brief and says which one it would pick. The tool builds the four options the rep sees: A, B, a "decide for yourself" that quotes the recommendation back, and a free-text "something else". The rep clicks and the run continues.

Options must be drawn from the vocabulary the engine actually scores — an off-vocabulary audience term silently collapses to neutral, which is the exact failure the question exists to prevent, so the tool rejects it. A dry cleaner and a nightclub do not get the same two options.

After the run
Every answer ends in costed suggestions

A Worth considering section, last, after the package is complete and quotable — two or three items, each one line, each carrying the number that makes it worth doing. "The plan leaves 47% of budget unspent because reach saturated at 53 stops — widening to the airport corridor would add roughly 40 more" is useful. "Consider broadening the geography" is not, and is explicitly disallowed.

The rep must be able to ignore that section entirely and send the package as it stands. It is a nudge, never a caveat that makes the plan provisional.

Before the call
It briefs the rep on their own client

Name the advertiser and the agent pulls their negotiation history: what they have actually paid relative to comparable inventory, judged against its own standard error, and what they have objected to on price. 96% of accounts are repeat business, so there is nearly always real history.

It is advisory by design and says so — it may suggest an opening multiplier and only the rep may apply it. And it leads with the honest statistic: deals lost to price were asking for about a third off, so a few percent is not what loses business.

2 · DuckDB in the backend — nobody opens a spreadsheet again

The problem statement's own description of today's workflow starts with "the rep opens a spreadsheet". Our answer is architectural: the 14 source tables are registered as DuckDB views and queried with SQL — columnar, vectorised, in-process, zero-copy, and never loaded into a workbook or a pandas frame in full.

What it buysWhy it matters here
165 MB, none of it openedIncluding a 124 MB / 2.05 M-row ridership table that would freeze Excel and take minutes through a naive CSV read. DuckDB scans only the columns a query touches.
The joins happen once, in SQLEleven derived analytical views — stop weights, site grouping, schedule blocks, route and corridor demand, screen profile, POI attachment — so the Python layer receives finished features instead of re-deriving a fourteen-table join per request.
Zero infrastructureNo warehouse to provision, no cluster, no credentials, no network hop. Judges can clone and run it; a sales team could too. It also means the whole analytical layer is reproducible from the CSVs on any machine.
Graceful degradationThe optional ridership table may be absent. The system detects that, falls back to scheduled estimates, and reports which source is live on the health endpoint and in its own model description — rather than returning quietly different numbers.
Room to growThe same SQL runs against Parquet, S3 or Postgres with a changed source clause. Scaling to more cities is a data-volume problem DuckDB is built for, not a rewrite.

Strict monorepo boundaries; one module per agent; Pydantic v2 contracts at every seam; full type hints; ruff for lint and format; a documented layering rule that engines never import tools and tools never import each other. 4 · Multiple models, chosen per request by the person doing the selling

Two providers and three models, selectable from the sidebar and remembered per rep. This is not a checkbox — it is a resilience decision made after being burned by a free-tier daily quota mid-run.

  • The catalogue is a backend fact. GET /models serves it, and the UI holds no copy — whether a provider has credentials is something only the server knows, and a stale client list offers the rep an option that fails.
  • Unconfigured providers are still listed, with the missing environment variable named. More actionable than an option that quietly vanishes.
  • Switching model mid-conversation keeps the conversation. One compiled graph is cached per selection, and all selections share one checkpointer, so a Gemini turn replays cleanly into an OpenAI one.
  • Rate limiting is mandatory and correctly scoped — one shared limiter across the Master and both specialists within a provider (the quota is per project), never shared across providers (the two caps differ fivefold).
  • Failures map to honest statuses through provider-agnostic exception bases, so the mapping survives a vendor swap: 429 quota, 503 upstream, 502 credentials with the right variable named, 400 for a stale model id.

5 · Export integrations that finish the rep's job

A recommendation the rep then has to retype into a proposal has not saved anyone any time. Two exports close that gap, and both are deliberately template-rendered from the verified run record rather than generated by a model.

Export
The client-facing proposal document

A purpose-built print layout — not the app window sent to a printer. Screens, places, clock times, per-line cost, totals and the delivery estimate.

What a client deliberately never sees: price bands and where in one we quoted, occupancy, booking probability, relevance scores, the solver and its gap, and any pricing lever the rep applied. That is the seller's position in a negotiation the client is on the other side of, and leaking it would be worse than not exporting at all.

Export
The sell email, drafted and editable

Opens instantly, costs zero tokens, and goes out via clipboard or the rep's own mail client. Short by design: what they get, what it costs, one reason to say yes, one ask.

Because it is filled from the run record it cannot quote a price the optimizer did not produce — and the rep edits it before sending, because they know the client and we do not.

Behind both sits the Evidence Inspector: four tabs (D1 audience, D2 relevance, D3 pricing, D4 optimizer) exposing the actual artifact rows behind every claim, so a rep challenged on a number can produce the row that produced it. And when an artifact is genuinely missing, the inspector says so — an earlier version swallowed the error and rendered an empty table while still reporting 250 rows, which is the one failure mode worse than an error message.

6 · A full Next.js application, in a three-day window

Not a Streamlit page and not a notebook. A real single-page product on Next.js 15 (App Router), React 19, TypeScript and Tailwind 4, with three resizable panels, streaming orchestration, restored transcripts and a persisted session rail.

Streaming, not spinning

Server-sent events drive a live stage rail through all six stages. The session is named and the user's message persisted before the first model call, so a turn that dies on a quota error still records what was asked — and the rail never sits on a placeholder for 90 seconds.

Nothing is lost on reload

Transcripts are stored server-side with each turn's metadata — run id, tool trail, token usage, and whether the pipeline actually ran. A restored follow-up therefore does not re-render a metrics deck for an answer that changed nothing, exactly as in the live stream.

Fast because we measured it

The "the UI takes 5–6 seconds" complaint was one hostname: uvicorn binds IPv4, and on Windows a connection to the IPv6 loopback is dropped rather than refused. Same four-request path, host as the only variable — 8.18 s via localhost, 0.053 s via 127.0.0.1. Two N+1 request patterns went with it.

7 · LangGraph Deep Agents as the framework — a considered choice

We evaluated the agent SDKs available to us and chose LangGraph's Deep Agents pattern. On this workload — long-horizon orchestration over analytical tools rather than code generation — it gave us the better result, and three structural properties we were not willing to give up:

  • A supervisor with real sub-agents. The Master genuinely delegates, and each specialist carries its own prompt, its own tool surface and its own guardrails. Our ML agent is told what it does not own — audience volume — and that boundary is enforced by the tool surface, not by hope.
  • A graph we control, with checkpointing. Multi-turn sessions, mid-conversation model switching, and a compiled graph cached per selection all fall out of the runtime rather than being bolted on.
  • Provider neutrality. Chat clients are constructed explicitly from our own settings, so the provider is a per-request choice rather than a deployment-time environment variable. That is what made the two-provider resilience story possible at all.
  • Observability for free, correctly scoped. One callback handler registered once in the run config traces the Master and every subagent, because callbacks propagate — so every run ends with a token and call summary that also comes back in the API response.
And the discipline we kept on top of the framework

Run handles, not payloads. Every tool takes a run_id. Specs, artifact references, packages and validation reports live in run state and the artifact store, so a 250-row candidate table and a 750-row price table never enter a model's context. That single rule is why a seven-stage orchestration over 11,163 screens fits in a small token budget — and why the numbers a rep reads are the numbers the engines computed, not a paraphrase of them.

09Logical correctness: four systems in harmony

The architecture is not four models bolted together. It is one orchestrator that understands the brief, and three specialists each of which owns exactly one question and is forbidden from answering anyone else's.

9.1 · The Master Agent reads the brief properly, then gets out of the way

  • The attachment is read before anything else. Uploads used to be accepted and never read — the agent's file tools addressed a virtual state filesystem, not the disk, so a staged RFP was unreachable and raw PDF bytes would not have helped anyway. Now every readable document is parsed once at upload and reached through a single tool that returns a bounded excerpt, never the file.
  • Three formats, honestly. PDF, DOCX and TXT, because those are what a rep forwards. Formats with no parser are rejected with a clear error rather than attaching cleanly and contributing nothing. DOCX tables are read as well as paragraphs — briefs put the budget and the market list in a table about as often as in a sentence.
  • A scanned PDF and a locked PDF get different messages, because the rep's next action is opposite: retype the numbers, versus resend it unlocked.
  • Documents are data, never instructions. They come from a third party. A directive found inside a client deck is text to summarise, and the agent is required to mention that it noticed and carry on.
  • Anything the document implies but does not state goes into missing_information. A document is not a licence to guess — and the final answer names, in one line, every input that came from the agent's judgement rather than from the brief.
  • Context is extracted once and passed as a normalised spec to every worker. The specialists read their inputs from the run, so no number is ever re-interpreted from prose twice.

9.2 · The Audience + Relevance Engine leaves no data on the table

It shortlists screens from the brief using all five dataset layers — and these are the points worth challenging us on:

  • A route's riders are shared between its stops, not multiplied by them. The single most consequential number in the system. Crediting each stop with its route's whole ridership makes a corridor's stops sum to 20.4× that corridor's riders. Share-weighting brings it to exactly 1.00×. Correcting it cut fixed-screen volume 13–16× — and every reach figure we report with it. That is the intended outcome of getting it right, not a regression.
  • A pool is a site, not a location row. 910 stop-mounted location rows are 878 physical sites. Grouping on name alone over-merges by 31% because station names are a low-cardinality template; adding the serving-corridor set is correct on both counts. Merging makes our reported reach smaller and more honest.
  • Reach is never the sum of exposures. On the canonical pool, naive summation over-counts ~25×. Three independent implementations of the definition — solver, reporter, validator — agree, and none imports another.
  • Audience scores are graded, not binary. Occupation mix has five values and "mixed" is the most common of them, so a white-collar yes/no flag scored mixed identically to student. Three affinity maps now grade all five, and two audience terms that were reading the wrong column have their own.
  • The advertiser vertical is a closed vocabulary, enforced. It used to be free text, and every value the agent actually wrote missed — pinning 25% of every relevance score to a constant while the tool reported a perfectly normal-looking ranking. Now it is validated against the 13 real values, normalised for case and separators, with a test that stops the vocabulary and its POI map drifting apart.
  • Sparse and absent signals are neutral and disclosed. Screens with no booking history in a vertical, and vehicles which by construction have no nearby-POI set, score neutral and appear in defaults_applied — never a silent penalty and never an invented value. Any sub-score that comes back constant pool-wide is reported, because from the outside that state is indistinguishable from success.
  • Weak signals are quarantined rather than blended. Ambient footfall correlates only 0.12–0.26 with transit ridership and can disagree 20× at one location, so it is used as a tie-break and enters no impressions, reach or price figure. Blending it in would quietly undo the stop-share correction.
  • A zero means "not modelled", never "nobody there". No scheduled service starts between midnight and 4am, so measured volume in that block is zero for every screen — while 4.5% of real bookings sit there. The estimate for that block is published separately and excluded from every total, so no validated figure moves with an assumed constant. The agent is required to say what a zero means whenever it reports one.
  • Ties are broken at sort time, never inside the score, with the screen id last — which is what makes the artifact reproducible run to run.

9.3 · The Pricing Agent prices every screen × block on evidence

Nine steps, detailed in Figure 5. What makes it defensible rather than merely elaborate:

  • The band is what comparable inventory actually transacted at — the real distribution of 191,110 bookings, not a rate card and not a model's opinion. Floor, target and cap all come from that distribution.
  • Zone sits above city, and that was measured. Holding city, size, type and position fixed, the median contracted price still varies 1.87×–2.52× across zones of one city — so segmenting on city alone was quoting all of them off one blended band. Coverage supports the depth: 95.6% of bookings sit in a zone+daypart cell with n≥30.
  • A bundle is priced as a bundle. A non-bundle historical deal holds exactly one screen; a bundled one a median of twenty. A package this system builds is commercially a bundle, so quoting it off single-screen comparables reads ~3.8% high. It is also the first dimension surrendered when a cell is thin, because it is worth 6.5–9% against zone's 87–152%.
  • One dimension was tested and rejected — campaign duration, ~2% between the buckets most campaigns fall in once bundle is controlled, and non-monotone on thin cells. Documented in the code so nobody re-adds it on intuition.
  • Occupancy drives the price, and elasticity does not — for the measured reason in Figure 5. The textbook alternative degenerated to the cap for every screen.
  • Availability is the tightest single day of the flight, not an average. An average lets a plan sell a screen that is full on the launch day.
  • Lost deals are used where they are informative and nowhere else. They train the booking-probability diagnostic and they supply the honest negotiation statistic — deals lost to price wanted about a third off, deals lost to competitors 2.5%. What they do not do is set a price off 393 examples spread across thousands of segments.
  • Client history informs the rep, not the quote. Because price-driven loss rates are flat across leverage tiers, applying posture automatically would be pricing off the half of the finding that does not hold. And a missing price-gap reads as "not recorded" rather than "0% off" — which would tell a rep the exact opposite of the truth.
  • The demand-value model is the one signal allowed to disagree with history, capped at +15%, gated four ways, and never shown a price. It is also self-correcting: if a raised price stops a screen selling, occupancy falls and the formula pulls it back down on the next run.
  • Every quote carries its own audit trail — which fallback rung resolved the band, every multiplier applied, and every lever a human moved.

9.4 · The OR Optimizer finds the best package, and proves it

  • It is a real mixed-integer program, not a greedy fill, and it reports the solver, the objective, the optimality gap and whether optimality was proven. A feasible-but-unproven result says so rather than being dressed up as an optimum.
  • Reach is bounded exactly. R ≤ min(E, P) is two linear constraints with no fitted constant, so the solver maximises precisely the number the validator re-derives. The fitted saturation curve it replaced left measured audience on the table and turned a 0.1-second solve into a 30-second timeout.
  • Extra context from the Master lands as real constraints. Mandated zones become elastic coverage groups that report their shortfall by name; required dayparts become hard rows; the client's leasing structure becomes a hard per-screen slot ceiling.
  • The slot cap binds per screen per day, summed across blocks — the compliance reading, and the stricter one. The per-cell alternative lets a screen bought in two blocks take two slots and pass; measured on a 45-day brief, it did exactly that. And honouring it costs no reach, measured across four briefs, four cap levels and all four objectives.
  • A bundle is one joint decision. Screens, blocks and slot depths are chosen simultaneously under one budget against one pooled reach ceiling — never three independent picks stitched together.
  • Non-linearity is placed where it exists. Slot depth is linear (all six slots loop continuously through the block); the concavity is at the pool, where a shared crowd saturates. Getting this the right way round is what stops the plan buying depth on a stop it has already saturated.
  • No constraint is invented. The imported formulation carried a hard 90% spend floor that no brief declares; it became a relaxing ladder, and the level used is reported. With the floor hard and nothing else binding, the solver had been converting every leftover rupee into depth — 100% of budget spent, 112 exposures per person, and not one of those last rupees adding a single person to reach.
  • Unspent budget comes with its cause, and the two causes read very differently: audience saturation means the money cannot buy more people and must not be absorbed by padding, while a client's own slot cap costing reach is a trade-off that belongs to the client. The agent may never offer to relax the client's constraint just to spend money.
  • The reach-versus-frequency trade-off belongs to the human. compare_objectives puts the plans side by side with real figures rather than picking one silently — and it withholds any profile whose exposures per person exceed the wear-out cap, reporting the measurement and the reason, while never withholding or substituting the campaign's own stated objective.
  • Infeasibility is an answer. Reason codes, a plain explanation, and the specific relaxation that would work. Never a plausible-looking package assembled instead.
  • An honest substitution is declared. There is no conversion model in this data, so a conversion objective weights the audience engine's industry-to-POI context score as a proxy — and the agent is required to say so rather than present the result as a conversion optimum.

9.5 · The verification layer — the reason any of this is quotable

The Master validates every specialist output before answering. Nineteen deterministic checks, run without exception, each re-deriving its quantity independently of the code that produced it.

Check familyWhat it re-derives, from scratch
CostLine costs from unit price × slots × days, the total from the lines, and the total against the brief's budget.
ReconciliationEvery reported aggregate against the lines it claims to summarise.
ReachThe pooled definition recomputed from the artifacts — the third independent implementation, and the one that would catch the other two drifting.
InventoryEvery selected screen exists, no duplicated screen×block line, slot depth within capacity.

Two rules that keep verification meaningful

A validated number may not depend on an assumed constant. If a figure the validator checks moves with a constant nobody can measure, the check validates nothing about the one thing that is genuinely uncertain. This is why the saturation constant reaches only a labelled diagnostic, and why the block-1 estimate is excluded from every total.

A constraint the brief declares gets a check, or it is not enforced. We learned this the hard way: a client asked for one rotating slot per screen, the package shipped three, and every layer reported success while the constraint sat visible in the spec the whole time. Without an independent re-derivation, nothing surfaces a silent miss.

10The feedback loop

The rep knows things the brief does not say. A system that cannot absorb that is a report generator, not a colleague — so the loop is a first-class part of the architecture, not a comment box.

How it scales past three cities

Inventory volume
The columnar layer absorbs it

Scoring is a set of SQL aggregations over views, so ten times the screens is a data-volume problem DuckDB is built for. Nothing in the feature layer is per-screen Python.

New geographies
No hard-coded places

Cities, zones and corridors are resolved from the data at request time, and unresolvable place names are surfaced before a run starts. A new city is new rows, not new code. The terminus weighting only redistributes riders within a route, so it transfers to a network with different topology.

Solve size
Controlled deliberately

The candidate pool is a stated truncation with a reported composition, and pool cell depth is bounded on purpose — measured, raising it added spend and frequency without adding a single person to reach. Latency versus quality is a knob we can defend the position of.

Context budget
Flat in inventory size

Because tools exchange run handles and artifact ids, token cost does not grow with the number of screens. Twenty thousand screens cost the same context as eleven thousand.

Throughput
Rate limits, not compute

The binding constraint on concurrent reps is the model provider's per-minute cap — which is precisely why two providers are wired and why the limiter is shared per provider. Adding a provider adds headroom without a code change.

Safety
Uploads treated as hostile

Type and size validated, never executed, never passed whole into context, and the extracted text bounded while it accumulates — because a 20 MB DOCX is a zip that decompresses to far more, and building the whole string first turns an upload limit into a memory problem.

Honesty as an engineering property

The most unusual thing about this codebase is how much of it exists to stop the system sounding more confident than it is. A short list, all of it live:

  • No stage is a stub and none is a heuristic. Every artifact carries provenance="computed", and the stub-reporting plumbing is retained precisely because it is the mechanism that would surface a regression.
  • Quarantined figures stay quarantined. Two internal proxies are carried for diagnostics and mapped onto no client-facing field, with names that make misuse obvious — one because its fixed and mobile paths are on different units (a ~36× gap), the other because it correlates only weakly with ridership.
  • Known limitations are surfaced by the system itself, not just written in a document: the demand source actually live, every default applied, any sub-score that came back constant, the pool's achieved composition, the assumption behind the mobile audience figure, and the absence of a held-out accuracy metric — which is exactly why no stage emits a per-screen confidence it cannot support.
  • The agent is forbidden from stating a number no tool returned, and forbidden from naming a screen without citing a real attribute of it. A checking tool exists for that, and it is called before the answer is written.
  • Plain English, undiminished caveats. The Master writes for a rep on a call — "screens at the same stop see the same people, so these are people reached, not views added up" — and a banned-vocabulary list keeps internal identifiers off a client-facing screen, with a test enforcing it. Simplify the language, never the caveat.
  • Rejected alternatives are documented with the measurement that rejected them, at the site of the decision. That is why a future contributor does not re-add the elasticity-argmax pricing, the duration segment, the volume discount, or the per-cell slot cap on intuition.
